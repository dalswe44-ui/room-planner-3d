## 1. 활용 배경 및 문제 정의

> 심사: 창의성·독창성(25), 문제해결 효과성(25) 가운데 "무슨 문제였나"에 답하는 절.

**기록에 있는 사실**
- 만든 것은 방 치수를 입력(mm·cm·m 전환)해 3D로 확인하고, 치수를 입력한 가구를 미리 배치해 보는 웹앱이다. 1인 개발이다. ([로그], docs/HEAD.md)
- 사진은 참고 이미지로만 쓴다. 사진 한 장에서 방 구조를 자동으로 뽑는 검증된 방법을 조사에서 찾지 못했기 때문이다. 그래서 "사진으로 3D를 만든다"는 표현은 쓰지 않는다. ([결정] 2026-11-16)
- 이 결정은 사용자의 아이디어로 한 단계 넓어졌다. 사용자는 굿노트로 치수를 적어 그린 배치도를 넣으면 방과 가구가 반영되게 하자고 제안했고(2026-11-16 23:04), 사진을 찍더라도 치수는 직접 입력하는 형식으로 하자고 정했다(23:20). 헤드(Claude)는 적힌 숫자를 읽는 일은 사진에서 치수를 추정하는 일과 다르다고 설명하고 두 방법을 제시했다. 사용자는 "AI가 읽어 만든 JSON을 앱에 붙여 넣는 방식(서버·API 키 없음)"을 골랐다. ([로그] 23:04, 23:20, [결정])
- 설계서는 기존 제품과의 차이로 Planner 5D 리뷰의 불만(크기 변경, 유료 가구)과 IKEA Kreativ의 한계(아이템 크기 변경 불가)를 적었다. 한국 제품의 현재 상태는 확인하지 못했으므로 "기존에 없던 것"이라고 쓰지 않는다. ([설계])

**채울 곳**

- [사용자 작성 필요] 앱이 없을 때 어떻게 가늠했는가(줄자, 눈대중, 종이 스케치)와 실제로 틀렸던 일.

## 2. 사용한 생성형 AI 도구 및 선택 이유

> 심사: AI 활용의 적절성(30) 가운데 "도구 선택".

**기록에 있는 사실**
- 도구는 Claude의 클라우드 세션이고, 헤드 에이전트 1개가 하위 에이전트 5개(spec-report, room-input, scene-engine, furniture-placement, qa-verifier)에게 일을 맡기는 구성이다. 이 구성은 사용자가 요청했다. ([로그] 2026-11-16 20:19 원문, [결정] 첫 줄)
- 하위 에이전트는 일의 단계가 아니라 소유 폴더로 나눴다. 버린 대안은 기획·구현·테스트의 단계별 분할과 실험 기능인 agent teams다. ([결정] 첫 줄)
- 이 구조의 비용도 설계서에 적혀 있다. 설계서가 인용한 자료 기준으로 멀티 에이전트는 같은 작업에 토큰을 3 ~ 10배 쓰고 모듈이 같은 상태와 좌표계를 공유하는 코딩에는 덜 맞는다. 기대한 실익은 속도가 아니라 맥락 분리와 독립 검증이었다. ([설계] "5개 구조의 비용과 절충")
- 앱 기술: Vite, React 19.3.1, three 0.187.0, @react-three/fiber 9.8.2, @react-three/drei 10.7.9, zustand 5.1.0. 백엔드, 로그인, API key가 없다. ([결정] 버전 고정 줄, CLAUDE.md)
- AI가 쓴 설계서의 버전 선택이 설치에서 틀린 사례: TypeScript 7.0.2는 typescript-eslint 8.72.2의 peer 범위(`>=4.8.4 <6.1.0`)와 맞지 않아 6.0.3으로 바꿨다. npm registry에서 직접 확인했다. ([결정])
- 배치도 읽기에 쓰는 AI는 앱 안에 들어 있지 않다. 사용자가 자기 AI 도구에 그림과 앱이 주는 문구를 넣고, 돌려받은 JSON을 앱에 붙여 넣는다. 그래서 앱에는 서버나 API key가 없다. ([결정] 사용자 결정 줄, [보고] T-007)
- 기록에 남은 실행 모델 ID는 `claude-fable-5-2`다(하위 에이전트가 환경에서 확인). 세션 중에 사용자가 헤드 모델을 바꾼 일이 있다(대화 기록). 프롬프트 파일 머리의 `model: sonnet` 지정은 이 실행 방식에서는 적용되지 않았다. ([로그] T-001 결과)
- pstack 점검(3.4)에서는 pstack의 다른 모델 패널(예: Gemini)을 이 환경에서 쓸 수 없어 같은 모델로 실행했다. 점검자가 만든 쪽과 같은 모델이라는 한계가 있다. ([로그] 00:50)

**채울 곳**
- [사용자 작성 필요] 실제로 쓴 모델 이름과 요금제. 위의 모델 ID가 맞는지 확인한다.
- [사용자 작성 필요] 이 도구를 고른 본인의 이유, 이전 경험.
- [사용자 작성 필요] 헤드 1 + 하위 5 구조를 요청한 이유.

### 3.3 핵심 프롬프트 발췌

- **위임 메시지의 구조.** 예로 T-002(room-input)의 위임은 목표, 범위(파일 목록), 읽을 것(SPEC 항목 번호와 CONTRACT 절 번호), 쓸 수 있는 인터페이스, 완료 기준 7개, 실행할 검증, 하지 않을 것을 담는다. 완료 기준은 "확정할 때 거부되는 값과 오류 문구의 허용 범위 숫자", "누르는 요소의 높이 44px 이상"처럼 확인할 수 있는 문장이다. 전문은 [로그] T-002 항목에 있다.
- **임시로 정한 값을 위임 메시지에 박는 방식.** T-001 위임은 사용자 부재로 헤드가 정한 값(허용 범위 500 ~ 20000 mm, 경고 조건 1000 mm 미만·15000 mm 초과, 격자 10 mm 등)을 그대로 적고 "(사용자 확인 필요)"를 붙이게 했다. ([로그] T-001)
- **"하지 않을 것" 줄.** 모든 위임에 있다. 예를 들어 T-003에서 "스냅·겹침 판정·가구 위치 확정(furniture-placement의 일)"을 명시해 모듈 경계를 지켰다. ([로그] T-003)
- **결함 수정 위임의 방식.** T-018은 pstack의 "근본 원인을 고친다" 원칙을 지시에 넣어 재현, 근본 원인, 증거를 보고하게 했다. 회귀 시험은 헤드가 넣었다. ([로그] T-018, [보고] T-018)
- **배치도 읽기 프롬프트.** 3.4 사례 B에 1차와 2차의 차이가 있다. 전문은 src/contracts/layoutImport.ts.

- 사진에서 방 구조나 치수를 뽑지 않는다. 치수는 전부 사용자가 입력하거나 사용자가 붙여 넣은 JSON에서 온다. ([SPEC] 3절) 배치도 읽기의 정확도는 시험 그림 1장으로만 확인했다(사례 B).
- 점검과 수정이 같은 모델 계열로 이루어졌다(2절).
- 실기기와 iOS Safari, 공개 URL을 확인하지 못했다.

### 4.4 이후 계획 (만들지 않은 것)

결과와 섞지 않는다. 후보는 [SPEC]의 범위 밖과 다음 작업 절, [설계] 표의 "제출 이후" 줄, [점검] 중 고치지 않은 항목(화면 기준 자석 범위, 방 안 제한, 클립보드·파일 선택 e2e, 장면 쪽 단위 테스트 약점)이다. 마감 시점에 만들지 않은 것만 남긴다.

## 5. 재현 방법 및 확산 가능성

> 심사: 재현성·확산성(20).

**기록에 있는 사실**
- 같은 프롬프트를 다시 실행해도 같은 코드가 나오지는 않는다. 재현할 수 있는 것은 산출물이 아니라 절차다. ([설계] "심사 배점 네 항목에 대한 대응")
- 절차 (이번 기록에서 실제로 돌아간 것만):
  1. 계약(타입, 단위·좌표 변환, 검증용 조회)을 먼저 쓰고 테스트로 고정한다.
  2. 소유 폴더별로 위임한다. 위임 메시지는 목표, 범위, 읽을 것, 완료 기준, 하지 않을 것을 담는다.
  3. 결과를 받으면 헤드가 typecheck·lint·test를 직접 돌리고 변경이 범위 안에 있는지 확인한다. 만든 쪽이 아닌 qa-verifier가 체크리스트를 숫자로 대조한다.
  4. 실제 앱과 배포 페이지를 직접 열어 자동 테스트가 못 보는 것을 찾는다(사례 F).
  5. 원칙 기반 독립 점검(사례 D)으로 점검하고, 사용자 결정과 충돌하는 것은 고치지 않고 묻는다.
  6. 시험은 커밋에 고정한 깨끗한 worktree와 별도 포트에서 돌린다(사례 E).
  7. 결함은 원인과 증거를 적고 회귀 시험을 추가한다. 회귀 시험은 수정을 되돌렸을 때 실패하는지 확인한다(사례 F, [보고] T-020).
  8. 결정과 위임 전문을 기록 파일에 남긴다([결정], [로그]).
- 재료는 저장소에 있다: 프롬프트 6개와 공유 규약, 위임 메시지 전문([로그]), 결정과 이유([결정]), 계약과 계약 테스트(src/contracts/), 보고서([보고], [QA], [점검]), 증빙([증빙]).
- 명령: `npm run dev`, `typecheck`, `lint`, `test`, `build`, `e2e`. e2e는 `E2E_PORT`로 포트를 바꿀 수 있고 실행마다 자기 빌드 폴더를 쓴다. `EVIDENCE_DIR`을 주면 증빙 스크린샷을 저장한다. (CLAUDE.md, [QA] T-017)
- 환경에 따라 달라진 점: 클라우드 세션에서는 하위 에이전트를 이름으로 부를 수 없어 머리말 방식을 썼다(T-007부터는 등록된 유형으로 실행했다고 기록). e2e는 내려받은 브라우저 대신 시스템의 Chrome을 쓴다. ([결정], [로그])
- 런타임 의존성의 라이선스는 MIT, Apache-2.0, ISC, BSD-3-Clause뿐이고 외부 저장소의 코드와 외부 에셋은 넣지 않는다. ([결정], CLAUDE.md) pstack은 프로젝트 밖에 받아 읽기만 했고 소스에 넣지 않았다. ([로그] 00:50)
- 이후 의존성에 idb-keyval(사진 저장)이 쓰이기 시작했다. 라이선스는 package.json과 node_modules에서 확인한 뒤 적는다. ([보고] T-015) [제출 전: 확인]
- README.md는 아직 재현 절차가 없다(8줄). 이후 작업이다.
- 소스 묶음은 node_modules와 .git을 빼고 만든다. git 이력에 작성자 정보가 들어 있기 때문이다. ([설계] "공개 URL 배포와 제3자 권리")
