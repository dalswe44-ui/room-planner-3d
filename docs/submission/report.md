## 1. 활용 배경 및 문제 정의

> 심사: 창의성·독창성(25), 문제해결 효과성(25) 가운데 "무슨 문제였나"에 답하는 절.

**가져올 곳:** [설계]의 "사진은 참고 이미지로만 쓴다"와 기존 제품 비교, [결정]의 사진 관련 줄, [측정]의 "활용 전" 기록.

**기록에 있는 사실**
- 만드는 것은 방 사진을 첨부하고 방 치수를 입력하면(mm·cm·m 전환) 3D로 방 구조를 확인하고, 치수를 입력한 가구를 미리 배치해 보는 웹앱이다. 1인 개발이다. (docs/HEAD.md) 사진 첨부는 2026-11-16 기준으로 아직 만들지 않았다([SPEC] 5절).
- 사진은 참고 이미지로만 쓰고 치수는 입력값만 근거로 삼는다. 사진 한 장에서 방 구조를 자동으로 뽑는 검증된 방법을 조사에서 찾지 못했기 때문이다. ([결정] 2026-11-16) 따라서 "사진으로 3D를 만든다"는 표현은 쓰지 않는다.
- 설계서는 기존 제품과의 차이로 두 가지를 출처와 함께 적었다: Planner 5D 리뷰에서 흔한 불만이 크기 변경과 가구가 유료로 잠겨 있다는 점이라는 것, IKEA Kreativ는 아이템 크기를 바꿀 수 없고 방을 만든 뒤 치수를 고칠 수 없다는 것. 한국 제품의 현재 상태는 확인하지 못했으므로 "기존에 없던 것"이라는 표현은 쓰지 않는다. ([설계] "심사 배점 네 항목에 대한 대응")

**채울 곳**
- [사용자 작성 필요] 이 문제를 고른 이유. 언제, 어떤 방에서, 어떤 가구를 두고 겪은 일인가.
- [사용자 작성 필요] 앱이 없을 때 어떻게 가늠했는가(줄자, 눈대중, 종이 스케치 등)와 그때 실제로 틀렸던 일.
- [사용자 측정 필요: [측정] 1절의 "종이와 줄자" 열. 배치안 하나를 검토하는 데 걸린 시간, 제한 시간 안에 검토한 배치안 수, 미리 발견한 문제 수, 계산 실수 수]

## 2. 사용한 생성형 AI 도구 및 선택 이유

> 심사: AI 활용의 적절성(30) 가운데 "도구 선택".

**가져올 곳:** [결정] 전체, [설계]의 "5개 구조의 비용과 절충"과 "기술 스택", [로그]의 사용자 지시 원문.

**기록에 있는 사실**
- 도구는 Claude의 클라우드 세션이고, 헤드 에이전트 1개가 하위 에이전트 5개(spec-report, room-input, scene-engine, furniture-placement, qa-verifier)에게 일을 맡기는 구성이다. 이 구성은 사용자가 요청했다. ([로그] 2026-11-16 20:19 원문, [결정] 첫 줄)
- 하위 에이전트는 일의 단계가 아니라 소유 폴더로 나눴다. 버린 대안은 기획·구현·테스트의 단계별 분할과 실험 기능인 agent teams다. ([결정] 첫 줄)
- 이 구조의 비용도 설계서에 적혀 있다. 설계서가 인용한 Anthropic 자료 기준으로 멀티 에이전트는 같은 작업에 토큰을 3 ~ 10배 쓰고, 모듈이 같은 상태와 좌표계를 공유하는 이런 코딩에는 덜 맞는 구조다. 기대한 실익은 속도가 아니라 맥락 분리와 독립 검증이다. ([설계] "5개 구조의 비용과 절충")
- 앱 쪽 기술: Vite, React 19.3.1, three 0.187.0, @react-three/fiber 9.8.2, @react-three/drei 10.7.9, zustand 5.1.0. 백엔드, 로그인, API key가 없다. ([결정] 버전 고정 줄, CLAUDE.md)
- 설계서는 TypeScript 7.0.2를 적었으나 typescript-eslint 8.72.2의 peer 범위(`>=4.8.4 <6.1.0`)와 맞지 않아 6.0.3으로 바꿨다. npm registry에서 직접 확인한 결과다. ([결정] 2026-11-16) AI가 쓴 설계서의 버전 선택이 실제 설치에서 틀린 것으로 드러난 사례다.
- 사진에서 방 구조를 뽑는 데에는 AI를 쓰지 않았다. ([결정] 사진 줄)

**채울 곳**
- [사용자 작성 필요] 실제로 쓴 모델 이름과 요금제. (도구의 종류와 유료·무료 여부는 점수에 영향이 없다고 [설계]가 공지를 옮겨 적었다.)
- [사용자 작성 필요] 다른 도구가 아니라 이 도구를 고른 본인의 이유, 이전에 써 본 경험.
- [사용자 작성 필요] 헤드 1 + 하위 5 구조를 요청한 이유.

- 빈 화면 단계의 공개 URL 첫 배포를 하지 못했다. 호스팅 계정 연결에 사용자 승인이 필요하다. ([로그] "하지 못한 것")

- 사용자가 프롬프트를 검토하기 전에 초안 그대로 실행됐다. ([로그])

## 5. 재현 방법 및 확산 가능성

> 심사: 재현성·확산성(20).

**가져올 곳:** README.md(아직 없다. 이후 작업), CLAUDE.md, 프롬프트 파일, [결정], package.json.

**기록에 있는 사실**
- 같은 프롬프트를 다시 실행해도 같은 코드가 나오지는 않는다. 재현할 수 있는 것은 산출물이 아니라 절차다: 계약을 먼저 고정하고, 소유 폴더별로 위임하고, 만든 쪽이 아닌 에이전트가 숫자로 판정한다. ([설계] "심사 배점 네 항목에 대한 대응")
- 절차의 재료는 전부 저장소에 있다: 프롬프트 6개와 공유 규약(docs/HEAD.md, CLAUDE.md, .claude/agents/), 위임 메시지 전문([로그]), 결정과 이유([결정]), 계약과 계약 테스트(src/contracts/).
- 명령: `npm run dev`, `typecheck`, `lint`, `test`, `build`, `e2e`. (CLAUDE.md)
- 환경에 따라 달라진 점 두 가지가 기록돼 있다. 클라우드 세션에서는 하위 에이전트를 이름으로 부를 수 없어 머리말 방식으로 실행했고, e2e 테스트는 내려받은 브라우저 대신 시스템의 Chrome을 쓴다. ([결정]) 다른 환경에서 따라 할 사람은 이 두 곳이 다를 수 있다.
- 런타임 의존성의 라이선스는 MIT, Apache-2.0, ISC, BSD-3-Clause뿐이고, 외부 저장소의 코드와 외부 에셋은 넣지 않는다. ([결정], CLAUDE.md)
- 소스 묶음은 node_modules와 .git을 빼고 만든다. git 이력에는 작성자 정보가 들어 있기 때문이다. ([설계] "공개 URL 배포와 제3자 권리")
